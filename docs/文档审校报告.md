
## 八、核验命令陷阱（避免误判为「文档出错」）

1. `ls -1 _*.log _*.txt _* | wc -l` 会对同一文件**重复计数**（52 → 102）；应写 `ls -1 _* | wc -l`。
2. `ls -1 app/api/v1/endpoints/_*.py` 会**同时匹配 `__init__.py`**（17 → 18）；须加 `grep -v __init__`。
3. `grep -c "include_router" .../__init__.py` 把文件头注释行计入（40 → 41）；须用 `grep -c "app.include_router("`。
4. `grep -rn "\.delay(\|apply_async(" app/` 会命中 `celery_app.py` 的 docstring 注释；判定「未接线」**须排除注释行**。

## 九、审校结论

> **文档体系整体可信，但存在 1 处硬错误、3 处数据失真、2 处结构矛盾、4 处精度问题。**
>
> 最值得警惕的不是个别数字，而是**两类系统性偏差**：
> 1. **低估自身**——表数（55+ → 68）、测试文件数（100+ → 455）、工具数（11 → 14）、Docker 能力（「无」→「已具备」）全部是**低报**。这会系统性拉低对工程成熟度的判断，进而误导优化优先级。

>
> 因此本次审校确立一条硬规则：**文档中的「已落地 / 已启用」必须有调用点或运行时证据支撑；仅存在实现不足以判定为已落地。**

## 1. 系统定位

AI-TestMaster 是一套**AI 驱动的全生命周期测试平台**，覆盖「需求 → 测试点 → 测试用例 → 评审 → 自动执行 → 缺陷发现 → 回归」的完整闭环。

与传统测试平台的区别在于：**用例生成、定位自愈、失败分析、视觉校验**四条关键路径均引入了 LLM/多模态模型能力，而非仅做用例管理与执行调度。

## 4. 核心模块职责与协作

### 4.1 AI 能力层（`app/ai/`）

| 模块 | 职责 |
| --- | --- |
| `client.py` | **统一门面**：业务只需 `client.chat(...)`，模型选择/降级对上层透明 |
| `openai_client.py` / `_openai_async_client.py` | OpenAI 兼容协议实现（DeepSeek/Qwen/Kimi/GLM 均走兼容端点） |
| `fallback_client.py` | 主模型失败时按策略降级到备选模型 |
| `mock_client.py` | 测试/离线模式桩 |
| `base.py` / `exceptions.py` / `error_codes.py` | 抽象基类与错误码体系 |
| `call_log.py` | 调用审计（token 计量，是成本看板的数据源） |
| `business_functions.py` | 面向业务的语义化封装（用例生成/失败分析等场景函数） |

**设计要点**：业务层与厂商解耦；模型切换是配置行为，不需要改业务代码。

### 4.2 执行引擎（`app/services/test_execution_engine/`）

- 入口：`test_execution_engine_v2.py`（v2 兼容入口 re-export v1 的部分符号）。
- 结构：以 **Mixin 组合**拆分为 `action_executor_*_mixin`（basic / complex / hover_select / input_click / verify_captcha）、`step_executor_mixin`、`task_executor_mixin/`、`task_batch_executor_mixin/`、`api_setup_mixin/`。
- 移动端：`app/services/mobile_ai_executor.py` + `action_executor_mixin.py`（ADB）。
- 自愈：`app/services/agent/agents/locator_healing_agent.py`，采用**三级级联**策略（权重 0.4 坐标 / 0.4 属性 / 0.2 模型）。
- 实时反馈：执行期通过 WebSocket 推送步骤状态（`app/api/v1/endpoints/websocket.py`）。

### 4.3 Agent 域（`app/services/agent/`）

**5 个 Agent**（实测）：

| Agent | 职责 |
| --- | --- |
| `test_generation_agent` | 需求/测试点 → 用例生成 |
| `test_execution_agent` | 执行编排 |
| `failure_analysis_agent` | 失败根因分析 |
| `locator_healing_agent` | 定位自愈 |
| `visual_validation_agent` | 多模态视觉校验 |

配套：`base.py`、`_tool_executor.py`、`_registrations.py`、`_rollback_handlers.py`、`circuit_breaker.py`（熔断）、`loop_detector.py`（循环检测）、`audit_service.py`（审计）、`artifact_registry.py` + `artifacts/`（**6 类 artifact**：application_state / execution_state / failure_history / project_context / test_case / user_intent）。

> ⚠️ **已知状态**：`AgentOrchestrator` 当前**零调用者**；`endpoints/agents.py` 只做落库、不驱动 Runtime。即 Agent 域是「已建成的能力骨架，尚未接入主链路」——这是 R1 的核心工作项。

### 4.4 数据库访问层（`app/db/`）

**引擎（4 个）**
| 引擎 | 说明 |
| --- | --- |
| `primary_engine` | 同步主库 |
| `get_secondary_engine()` | 同步从库，**懒加载**；未配置 `DATABASE_URL_SLAVE` 时退化为 primary |
| `async_primary_engine` | 异步主库（渐进迁移用） |
| `get_async_secondary_engine()` | 异步从库，同懒加载退化策略 |

**sessionmaker 工厂（4 个）**：`PrimarySessionLocal` / `get_secondary_session_local()` / `AsyncPrimarySessionLocal` / `get_async_secondary_session_local()`

**会话依赖与上下文入口（8 个）**：`get_db`、`get_read_db`、`get_db_context`、`get_read_db_context`、`async_get_db`、`async_get_read_db`、`async_get_db_context`、`async_get_read_db_context`

**读写分离路由（3 个）**：`get_async_write_session`、`get_async_read_session`、`require_master`
**复制延迟监控（3 个）**：`get_current_lag`、`probe_replica_lag`、`start_lag_monitor`

**多租户隔离**：`app/core/tenant_query_filter.py` 提供行级过滤；`app/core/tenant_context.py` 提供请求期租户上下文。租户隔离由 Alembic 迁移 `20260730_add_tenant_isolation.py` 落地。

> ⚠️ **复杂度警示**：同步 + 异步 × 主 + 从 = 四象限组合，叠加 8 个会话入口，是当前工程复杂度的**主要来源之一**。测试侧 `conftest.py` 的 `_SyncBackedAsyncSession` 桥接类正是这一复杂度的直接投影（用同步引擎模拟异步会话，以便在同一套 fixture 下跑两种端点）。详见《架构优化与简化分析》§2.3。

### 4.5 权限校验（R0-3 归一后）

**唯一实现源**：`app/api/v1/endpoints/access_deps.py`

| 形态 | 签名语义 | 使用场景 |
| --- | --- | --- |
| `verify_project_access(db, project_id, current_user)` | 同步，403「无权限操作此项目」 | 同步端点 |
| `verify_project_access_async(db, project_id, current_user)` | 异步，403 | **参数来自 body/query、无法依赖注入**的端点 |
| `require_task_access(task_id, current_user=Depends(get_current_user), db=Depends(async_get_db))` | 依赖注入，404「测试任务不存在」+ 403「无权限操作此任务」，**返回 `TestTask`** | 路径参数为 `{task_id}` 的端点 |

`pipeline_deps.py` 以 re-export 方式对外保持 `verify_project_access` / `verify_project_access_async` 路径不变；`verify_iteration_access*` 仍留在 `pipeline_deps.py`（跨域，待后续统一）。

### 5.1 依赖方向（严格单向）

```
endpoints ──▶ services ──▶ crud ──▶ models
    │             │           │
    │             ├──▶ ai/ ───┘
```

## 6. 四大端到端数据流

### 6.1 登录认证（验证码 + JWT + Redis 黑名单）

```
① GET  /auth/captcha            → 生成验证码，写入 Redis（含 IP 限流计数）
② POST /auth/login              → 校验验证码 → 校验凭证 → 签发 JWT(access/refresh)
③ 后续请求                       → SecurityMiddleware 解析 JWT
                                 → 查 Redis jti 黑名单（登出/强制失效）
                                 → 注入 current_user + tenant context
④ POST /auth/logout             → jti 写入 Redis 黑名单直至自然过期
```

**口径说明**：配置默认 `JWT_ALGORITHM=HS256`，同时存在 `JWT_PREFERRED_ALGORITHM=RS256` 的**迁移机制**。因此「RS256 已落地」的表述偏乐观——准确说法是**默认 HS256，RS256 为迁移目标**。

### 6.2 AI 生成用例（需求 → 测试点 → 用例 → 评审）

```
上传需求文档
  → services/requirement   解析（docx/pdf/xmind，含 _file_extract 组合逻辑）
  → 测试点生成              SSE 流式：endpoints/test_point_import_stream.py
                            ai/client → LLM → 增量回传前端
  → 测试点确认/编辑          crud/test_point_*
  → 用例生成                endpoints/test_case_ai_stream.py
                            ai/business_functions + test_generation_agent
  → 用例落库                crud/test_case*
  → 质量检查                services/case_quality_*（评分 + 报告）
  → 评审                    services/review_inbox + review-workflow
```

**质量控制**：用例生成后经 `case_quality_check` / `case_quality_report` 双端点评分，低分用例进入评审 Inbox 冲突项列表。

### 6.3 自动执行（执行引擎 + WebSocket + 自愈）

```
选择任务/用例 → 装配执行环境 → 启动执行（进程内线程桥接，非 Celery）
  ├─ 浏览器/设备就绪
  ├─ 逐步骤执行（step → action mixin）
  │    ├─ 定位成功 → 执行动作 → 断言
  │    └─ 定位失败 → locator_healing_agent 三级级联（0.4 坐标 / 0.4 属性 / 0.2 模型）
  ├─ WebSocket 实时推送每一步状态与截图
  └─ 终态：结果落库 → 失败分析（failure_analysis_agent）→ 视觉校验（visual_validation_agent，可选）
                                          → 缺陷登记 → 报告生成
```

> ⚠️ **重要事实**：执行**并非**由 Celery 分布式消费，而是在**请求进程内以线程桥接**方式运行（`endpoints/test_task_exec.py`）。这决定了「执行隔离性」是当前最真实的架构短板（详见《架构优化与简化分析》§6）。

### 6.4 Pipeline 回归（含 TIA / AB / 成本看板）

```
Pipeline 触发
  → app/pipelines/runner.py 编排
     ├─ steps/      场景步骤（5 场景）
     ├─ prompts/    场景提示词
     ├─ _runner_executor / _runner_progress / _runner_metrics
  → 影响面分析（TIA）  services/agent/impact_analysis（纯算法，无 LLM）
  → 决策分派           decision_dispatch（固定枚举规则分派）
  → AB 实验            endpoints/ab_test + src/views/admin/AbTestDashboard.vue
  → 成本与度量         call_log → pipeline_metrics → 成本看板
  → 结果：pipeline_runs / pipeline_steps / pipeline_metrics 表
```

> 表名口径：均为**复数**（`pipeline_runs` / `pipeline_steps` / `pipeline_metrics`），早期文档中的单数 `pipeline_run` 属笔误。

## 7. 横切关注点

### 7.1 鉴权与权限
JWT（HS256 默认）+ Redis jti 黑名单；端点级通过 `Depends(get_current_user)` 注入用户，资源级通过 `access_deps` 三形态校验（见 §4.5）。

### 7.2 多租户
请求期租户上下文（`tenant_context`）+ 查询期行级过滤（`tenant_query_filter`）+ 迁移层隔离（`20260730_add_tenant_isolation`）。早期对标文档称「无多租户」已过期。

### 7.3 安全
`app/core/security_middleware.py` 提供 `SecurityHeadersMiddleware`、`HSTSMiddleware`、`CSPMiddleware`、`CSRFMiddleware`；密钥管理见 `app/core/secret_keys` / `key_management.py`；CI 含 `security-scan.yml`。

### 7.4 后台任务（**当前状态必须明确**）

| 能力 | 状态 | 依据 |
| --- | --- | --- |
| APScheduler 自测调度 | ✅ **在用** | `app/tasks/self_test_scheduler.py`（190 行），被 `endpoints/project_core.py` 引用 |
| 自测执行辅助 | ✅ **在用** | `app/tasks/_self_test_executor_mixin.py`（323 行），被 3 个测试文件引用 |
| Celery 分布式执行 | ❄️ **已冻结** | `CELERY_ENABLED=False`；全库**零** `.delay()`/`apply_async()` 实调用（唯一 2 处命中均为注释）；代码移至 `app/tasks/_frozen/`；依赖已从 `requirements.txt` 移除 |

**冻结的工程要点**：`app/tasks/_frozen/` 下的文件顶层 `import celery`，依赖已移除后**必然 ImportError**。由于 `pytest.ini` 为 `testpaths=tests` 且**无 `norecursedirs`**，若无保护措施，pytest 会收集到这些文件并导致**全量测试直接崩溃**。现有保护：`tests/conftest.py` 中的 `collect_ignore_glob = ["tasks/_frozen/*"]`。恢复方法见 `app/tasks/_frozen/README.md`（需整体移回 `app/tasks/` 并恢复依赖）。

## 9. 关键设计决策

| # | 决策 | 理由 | 代价 |
| --- | --- | --- | --- |
| D1 | 统一 AI 客户端门面 | 厂商可替换、降级集中 | 门面层需持续跟进各厂商协议差异 |
| D2 | 执行引擎以 Mixin 组合拆分 | 避免单类爆炸，按动作域隔离 | 继承链深、跳转成本高、IDE 提示弱 |
| D3 | 同步/异步双引擎并存（渐进迁移） | 允许老代码不动、新代码用异步 | 四象限组合 → 会话入口膨胀 + 测试桥接类 |
| D4 | 读写分离以「懒加载 + 退化」实现 | 未配从库时零额外开销 | 逻辑双份，`require_master` 易漏 |
| D5 | Agent 域独立建成（含熔断/循环检测/审计） | 为智能编排预留能力 | 当前**未接入主链路**，属「已建未用」 |
| D6 | 冻结 Celery 而非删除 | 保留未来进程隔离的执行路径 | 需 `_frozen` 收集保护，否则 pytest 崩 |
| D7 | 端点私有 `_*.py` 拆分文件承载逻辑 | 快速拆减单文件体积 | 业务逻辑未下沉 service，分层被穿透 |

## 10. 已知限制与风险（截至 2026-09-18）

1. **执行无进程隔离**：执行在请求进程内线程桥接，长任务占用 Web worker，无法多机扩展，且进程崩溃会带走执行状态。这是**唯一真正的架构级短板**。
2. **分层穿透**：`endpoints/` 下 17 个 `_*.py` 私有文件承载业务逻辑。
3. **会话层复杂度**：4 引擎 + 4 工厂 + 8 入口 + 3 读写路由，认知负荷高。
4. **Agent 域未接线**：`AgentOrchestrator` 零调用者，能力悬空。
5. **SAML 依赖缺失**：`python-saml`(onelogin) 未安装，导致 5 个 SAML 测试文件报 `ModuleNotFoundError`（环境问题，非代码缺陷）。
6. ~~根目录大量 `_*.log` / `_*.txt` 临时产物~~ → **已于 2026-09-18 R0-1 清理完毕**（清理清单见 `docs/archive/cleanup-manifest-2026-09-18.txt`）。
7. **文档跟踪风险**：本轮发生文档被外部进程 `git clean` 删除的事故，已确立「产出物一律先入库」的纪律。

### 命令陷阱（血泪教训）

1. `ls -1 _*.log _*.txt _* | wc -l` 会**重复计数**同一文件；须写 `ls -1 _* | wc -l`。
2. `ls -1 app/api/v1/endpoints/_*.py` 会**同时匹配 `__init__.py`**；须加 `grep -v __init__`。
3. `grep -c "include_router" ` 会把文件头注释计入；须用 `grep -c "app.include_router("`。
4. `grep -rn "\.delay("` 会命中 docstring；判定「未接线」须排除注释行。

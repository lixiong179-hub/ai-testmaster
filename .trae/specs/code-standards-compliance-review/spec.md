# 代码规范合规性审查与整改 Spec

## Why
当前项目存在不符合开发规范的问题，需要按模块功能全面盘点，识别不符合规范的问题点，制定整改计划，确保代码质量和可维护性。

## What Changes
- 按模块功能划分检查范围：API层、Service层、CRUD层、Model层、Utils层、前端模块
- 检查维度：代码风格、类型注解、安全规范、性能要求、AI生成约束
- 制定问题清单和整改任务
- 整改后自测+评审+优化闭环

## Impact
- 涉及项目所有代码模块
- 目标：所有代码符合项目开发规范

## 检查范围与标准

### 一、代码风格检查
| 检查项 | 标准 |
|--------|------|
| 命名规范 | 变量函数lowerCamelCase，类UpperCamelCase，常量UPPER_SNAKE_CASE |
| 缩进 | 4空格缩进 |
| 行宽 | ≤120字符 |
| 注释 | 公开方法必须有类型注解与文档注释，只注释业务原因与边界场景 |

### 二、语言规范检查
| 检查项 | 标准 |
|--------|------|
| Python类型注解 | 强制类型注解 |
| Python IO管理 | IO统一with管理 |
| Python字符串 | 只用f-string |
| TypeScript | 禁用any，强制空值处理，异步统一async/await |

### 三、架构设计检查
| 检查项 | 标准 |
|--------|------|
| 文件行数 | 单文件≤300行 |
| 依赖注入 | 依赖构造函数注入，禁止直接new实例 |
| 模块结构 | 新增模块遵循项目现有结构 |

### 四、安全红线检查
| 检查项 | 标准 |
|--------|------|
| SQL注入 | 零容忍，仅用参数化/列表传参 |
| 命令注入 | 零容忍 |
| 密钥管理 | 禁用硬编码，统一环境变量读取 |
| 日志脱敏 | 敏感字段必须脱敏 |
| 输入校验 | 所有外部输入必须经过模型校验 |

### 五、性能要求检查
| 检查项 | 标准 |
|--------|------|
| SQL执行 | 禁止循环内执行SQL，杜绝N+1 |
| 批量操作 | 批量写入使用batch |
| 查询优化 | 高频查询优先Set/Map |

### 六、AI生成约束检查
| 检查项 | 标准 |
|--------|------|
| 占位符 | 禁止TODO与空占位，未实现逻辑抛NotImplementedError |
| 异常处理 | IO、网络、解析强制异常捕获 |
| 空安全 | 深层属性必须空安全兜底 |
| 代码复用 | 重复逻辑自动抽工具方法 |
| 废弃代码 | 删除废弃注释代码 |
| 第三方库 | 标注安装命令 |

## 模块划分

### 后端模块
1. **API层** (app/api/v1/endpoints/) - API端点实现
2. **Service层** (app/services/) - 业务逻辑
3. **CRUD层** (app/crud/) - 数据库操作封装
4. **Model层** (app/models/) - 数据模型
5. **Schema层** (app/schemas/) - Pydantic模型
6. **Core层** (app/core/) - 核心配置
7. **Utils层** (app/utils/) - 工具类

### 前端模块
1. **API封装** (src/api/) - 接口封装
2. **组件** (src/components/) - 通用/业务组件
3. **Hooks** (src/hooks/) - 自定义Hook
4. **Utils** (src/utils/) - 工具类
5. **Views** (src/views/) - 业务页面

## 整改流程
1. 按模块检查 → 2. 制定整改任务 → 3. 执行整改 → 4. 自测验证 → 5. 评审确认 → 6. 优化完善 → 7. 下一任务

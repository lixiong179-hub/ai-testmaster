# 测试用例纠正功能 - Product Requirement Document

## Overview
- **Summary**: 建立从测试执行失败到用例纠正的完整闭环工作流，**智能区分用例问题和Bug问题**：用例问题（步骤异常、定位异常）提供纠正机制；Bug问题（执行正确但结果不对）明确提示并**禁止**用例纠正，避免混淆导致真实Bug被用例纠正掩盖。
- **Purpose**: 解决AI生成测试用例执行误差问题，同时**保护真实Bug不被误纠正**：通过智能分析区分用例问题和Bug问题，只对用例问题提供纠正功能，对Bug问题明确警告不要修改用例，确保测试用例既能持续优化，又能有效发现真实产品Bug。
- **Target Users**: 测试工程师、自动化测试开发人员、QA主管

## Goals
- 建立智能失败原因分析机制，区分用例问题和Bug问题
- 场景1（用例问题）：提供"执行失败→用例纠正→验证通过"的完整工作流
- 场景2（Bug问题）：明确警告并禁止用例纠正，防止真实Bug被掩盖
- 防止混淆：确保不会因为用例执行失败就盲目纠正用例，从而掩盖真实产品Bug
- 提供基于执行日志、截图、AI分析的智能判断建议
- 增强技术视图的可视化编辑功能，支持直接编辑定位信息
- 实现纠正后的快速验证功能，一键重跑验证
- 建立用例版本历史管理，支持修改追溯和回滚
- 保持与现有功能的无缝集成，不破坏现有流程

## Non-Goals (Out of Scope)
- 不实现全自动AI纠错（需要人工确认）
- 不实现用例批量纠正功能（后续可迭代）
- 不实现复杂的用例对比工具（后续可迭代）
- 不修改测试执行引擎的核心逻辑
- 不实现用例分享和协作功能（后续可迭代）
- **不实现**提Bug和Bug创建功能（使用现有Bug管理功能）
- **不允许**：执行失败就默认走用例纠正流程，必须先判断问题类型

## Critical Business Rule (最重要)
- **严禁**：只要用例执行失败就去纠正用例
- **必须**：首先分析失败原因，区分是用例问题还是Bug问题
- **场景1 - 用例问题**：步骤描述错误、定位信息错误、预期结果错误 → 走用例纠正流程
- **场景2 - Bug问题**：执行步骤完全正确、操作完全符合预期、但实际结果与预期不符 → **禁止**修改用例，明确提示这是Bug问题

## Background & Context
- 项目已有完整的测试执行功能：`TestExecution.vue` 页面支持执行、截图、视频录制、AI分析
- 项目已有完整的用例质量分析和审核功能：`case_quality.py` API提供质量分析、审核状态管理
- 项目已有双视图功能：刚刚恢复了业务视图/技术视图切换
- 项目已有Bug管理功能：`Bug` 模型支持关联用例和执行结果（用户可手动提Bug）
- 现有缺失：
  - 没有智能区分用例问题和Bug问题的机制
  - 执行失败后没有快速跳转纠正的入口
  - 技术视图只能查看不能编辑
  - 没有完整的纠正工作流

## Failure Type Classification (失败类型分类)

### 场景1：用例问题（Case Issue）
**特征**：
- 步骤描述不清晰或错误
- 元素定位信息错误（CSS选择器、XPath、AI坐标等）
- 预期结果描述错误
- 操作类型错误（应该点击但写成输入等）
- 前置条件不完整

**处理方式**：
- 显示"纠正用例"按钮
- 跳转到用例详情页技术视图
- 提供编辑功能
- 支持快速验证

### 场景2：Bug问题（Product Bug）
**特征**：
- 执行步骤完全正确
- 操作完全符合预期流程
- 元素定位成功（如果涉及UI操作）
- 但实际结果与预期结果不符
- 疑似产品功能缺陷

**处理方式**：
- **不显示**"纠正用例"按钮（或明确禁用）
- 显示强烈警告："这是Bug问题，不要修改用例！"
- 可以提供"手动记录Bug"的提示（引导到现有Bug管理功能）
- **禁止**任何用例修改操作

## Functional Requirements
- **FR-1**: 智能失败原因分析 - 基于执行日志、AI分析、截图等，自动判断是用例问题还是Bug问题，给出建议但保留人工决定权
- **FR-2**: 测试执行页面场景化按钮 - 用例问题显示"纠正用例"，Bug问题不显示"纠正用例"并警告，两种场景都显示"分析失败原因"
- **FR-3**: 用例问题流程 - 点击"纠正用例"跳转到用例详情页技术视图，定位到失败步骤
- **FR-4**: Bug问题流程 - 明确警告这是Bug问题，禁止用例纠正，不显示任何用例修改按钮
- **FR-5**: 技术视图强化编辑 - 支持内联编辑操作、预期结果、定位信息
- **FR-6**: 智能建议面板 - 显示失败原因、AI分析建议、前后截图对比
- **FR-7**: 快速验证功能 - 用例纠正完成后可一键重跑验证
- **FR-8**: 用例版本历史 - 记录每次修改、支持版本对比、支持一键回滚
- **FR-9**: 快速添加定位 - 一键补充缺失的元素定位信息
- **FR-10**: 工作流状态管理 - 用例问题：执行失败→纠正中→验证中→验证通过

## Non-Functional Requirements
- **NFR-1**: 从执行失败到进入处理页面的跳转时间 < 2秒
- **NFR-2**: 技术视图编辑操作响应时间 < 500ms
- **NFR-3**: 快速验证的步骤选择器体验流畅
- **NFR-4**: 版本历史列表加载时间 < 1秒（最近20个版本）
- **NFR-5**: UI设计保持与现有页面风格一致
- **NFR-6**: 操作有明确的加载状态和反馈提示
- **NFR-7**: 失败类型判断有明确的视觉标识，避免混淆
- **NFR-8**: Bug问题场景下，警告提示足够强烈，醒目且不易忽略

## Constraints
- **Technical**: 前端使用 Vue3 + TypeScript + Element Plus；后端使用 FastAPI + SQLAlchemy + MySQL
- **Business**: 必须保持与现有代码风格一致，不破坏现有功能
- **Critical Business Rule**: 必须严格区分用例问题和Bug问题，严禁混淆
- **Dependencies**: 依赖现有的测试执行API、用例质量API、技术视图服务

## Assumptions
- 现有测试执行功能正常工作，能记录失败状态和AI分析
- 现有技术视图API能正常获取和展示定位信息
- 现有用例编辑API可正常使用
- 用户有足够的权限修改测试用例
- AI分析结果能提供一定的失败原因判断依据
- 现有Bug管理功能满足用户手动提Bug的需求

## Acceptance Criteria

### AC-1: 智能失败原因分析显示
- **Given**: 用户在测试执行页面，某个步骤执行失败
- **When**: 页面显示执行结果
- **Then**: 显示失败原因分析，包含AI建议的问题类型（用例问题/Bug问题），但保留人工选择权利
- **Verification**: `human-judgment`

### AC-2: 场景1 - 用例问题显示"纠正用例"按钮
- **Given**: 用户判断或AI建议是用例问题
- **When**: 页面显示执行结果
- **Then**: 显示"纠正用例"按钮，**不显示**任何警告
- **Verification**: `human-judgment`

### AC-3: 场景2 - Bug问题不显示"纠正用例"并强烈警告
- **Given**: 用户判断或AI建议是Bug问题
- **When**: 页面显示执行结果
- **Then**: **不显示**"纠正用例"按钮，有明确的、醒目的警告提示"这是Bug问题，不要修改用例！"
- **Verification**: `human-judgment`

### AC-4: 用户可以切换问题类型判断
- **Given**: AI建议了问题类型
- **When**: 用户不同意AI的判断
- **Then**: 用户可以手动切换问题类型（从用例问题切换到Bug问题，或反之）
- **Verification**: `human-judgment`

### AC-5: 点击"纠正用例"跳转到详情页并定位到失败步骤
- **Given**: 用户点击"纠正用例"按钮
- **When**: 页面跳转
- **Then**: 跳转到用例详情页，自动切换到技术视图，自动高亮/定位到失败的步骤
- **Verification**: `human-judgment` + `programmatic`

### AC-6: Bug问题场景下详情页禁止用例修改
- **Given**: 用户从Bug问题场景进入详情页
- **When**: 页面加载
- **Then**: 详情页显示警告提示，所有编辑按钮禁用或隐藏，技术视图表格不可编辑
- **Verification**: `human-judgment` + `programmatic`

### AC-7: 技术视图支持内联编辑
- **Given**: 用户在技术视图页面，且不是Bug问题场景
- **When**: 用户双击单元格或点击编辑图标
- **Then**: 单元格进入编辑状态，用户可修改操作、预期结果、CSS选择器、XPath等
- **Verification**: `human-judgment`

### AC-8: 显示智能建议面板
- **Given**: 用户在技术视图页面，且该用例有失败的执行记录
- **When**: 页面加载
- **Then**: 显示智能建议面板，包含失败原因、AI分析建议、执行前后截图对比
- **Verification**: `human-judgment`

### AC-9: 快速验证功能正常工作
- **Given**: 用户完成用例纠正
- **When**: 用户点击"快速验证"按钮
- **Then**: 弹出验证对话框，支持选择要验证的步骤，确认后启动快速验证执行
- **Verification**: `human-judgment` + `programmatic`

### AC-10: 用例版本历史正常显示
- **Given**: 用户在技术视图页面
- **When**: 用户点击"版本历史"按钮
- **Then**: 显示版本历史列表，包含修改人、修改时间、修改内容
- **Verification**: `human-judgment` + `programmatic`

### AC-11: 版本对比和回滚功能正常
- **Given**: 用户在版本历史页面
- **When**: 用户选择两个版本进行对比，或点击某个版本的"回滚"按钮
- **Then**: 显示版本对比差异，或确认后回滚到指定版本
- **Verification**: `human-judgment` + `programmatic`

### AC-12: 快速添加定位功能正常
- **Given**: 用户在技术视图，某个步骤缺少定位信息
- **When**: 用户点击"添加定位"按钮
- **Then**: 显示定位添加对话框，支持快速添加CSS/XPath/AI坐标
- **Verification**: `human-judgment`

### AC-13: 纠正工作流状态正确更新
- **Given**: 用例执行失败进入纠正流程
- **When**: 用户进行各种操作（开始纠正、验证、验证通过等）
- **Then**: 用例状态正确更新（执行失败→纠正中→验证中→验证通过）
- **Verification**: `programmatic`

### AC-14: Bug问题不会错误地进入用例纠正流程
- **Given**: 明确标记为Bug问题
- **When**: 用户在任何环节
- **Then**: 系统不会建议或允许用例纠正操作，始终显示警告提示
- **Verification**: `human-judgment` + `programmatic`

- [ ] 版本回滚是否需要创建新版本，还是直接恢复？
- [ ] AI分析的可信度如何？是否需要人工审核所有判断？

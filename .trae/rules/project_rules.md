# 项目开发规则
## 核心原则
真实环境测试、禁止 Mock、覆盖率≥95%；最小改动、外科手术式修改、杜绝冗余。

## 一、代码风格
变量函数lowerCamelCase，类UpperCamelCase，常量UPPER_SNAKE_CASE；4空格缩进，行宽≤120。
公开方法必须加类型注解与文档注释，只注释业务原因与边界场景，禁止无效注释。

## 二、语言规范
Python：强制类型注解，IO统一with管理，字符串只用f-string。
TS：禁用any，强制空值处理，异步统一async/await。

## 三、架构设计
单文件≤350行，若代码粘性高（如业务逻辑复杂），可放宽考虑拆分模块；依赖构造函数注入，禁止直接new实例；新增模块遵循项目现有结构。

## 四、安全红线
SQL、命令注入零容忍，仅用参数化/列表传参；密钥禁用硬编码，统一环境变量读取；
日志脱敏敏感字段；所有外部输入必须经过模型校验才可进入业务。

## 五、性能要求
禁止循环内执行SQL，杜绝N+1；批量写入使用batch；高频查询优先Set/Map。

## 六、测试规范
核心分支覆盖率≥95%；代码同步配套正常、空值、异常、边界用例；
使用真实测试库，用例执行后自动清理测试数据。

## 七、AI生成约束
禁止TODO与空占位，未实现逻辑抛NotImplementedError；
IO、网络、解析强制异常捕获；深层属性必须空安全兜底；
重复逻辑自动抽工具方法；删除废弃注释代码；第三方库标注安装命令。

## 八、修复与合并
Bug修复定位根因，只改必要代码并补充验证用例；
合并需全量测试、类型检查无错、CR通过；依赖锁定版本，库表变更附带迁移与回滚。

## 九、会话连续性
当新会话携带上一轮快照（conversation summary）启动时，必须按以下流程工作：

1. **读取状态文件**：优先读取 `.trae/session_state.json`，获取 `last_commit` 和 `modifications` 清单。
2. **增量差异验证**：运行 `git diff <last_commit>..HEAD -- <相关文件>`，仅关注差异部分，
   快照中记录的代码片段可能已过时，以 git diff 结果为准判断哪些已修、哪些仍待修。
3. **精准定位**：对快照中提到的每个待修项，只读对应文件的关键函数验证当前状态，
   禁止全量重读所有文件。若 diff 显示该文件未变更，则快照中的描述仍有效；
   若 diff 显示该文件有变更，则以当前代码为准。
4. **更新状态文件**：每次修改完成后，更新 `.trae/session_state.json` 中的
   `last_commit`（改为当前HEAD）、`modifications`（追加本次修改）、`verified`（测试结果）。
5. **快照代码片段的使用原则**：快照中的代码片段仅作为"问题方向指引"，
   不得直接用于编辑操作。编辑前必须先读取文件当前内容确认。
